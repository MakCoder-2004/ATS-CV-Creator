Broader synthetic layouts are needed before claiming representative automatic proposal feasibility. PDF.js is viable for bounded text extraction but does not resolve layout/hyperlink association. `docx` is a writer, not a reader.

## DOCX parser and safety candidate

The bounded candidate tested is JSZip 3.10.2 for ZIP inspection, preflight before XML parsing, then Mammoth 1.13.0 for inert OOXML text/HTML extraction. `Mammoth` is not present in package manifests; it is experimental and must pass dependency/security review. Harness preflight rejects (all passed): `../` original ZIP path (JSZip `unsafeOriginalName`), DTD/entity declaration, external image relationship, byte-limit violation, ZIP entry-count limit and uncompressed-size limit. Ordinary external hyperlink relationships remain data and are displayed, never dereferenced. Exact observed tests: normal fixture accepted; each of seven prohibited/over-limit cases (path, DTD, external image relationship, macro payload, byte cap, entry cap, expanded-size cap) rejected with its expected code. Mammoth throws on the malformed XML fixture. These are small representative rejection probes, not a proof against parser/resource attacks.

These tests substantiate that the *harness policy checks* detect those synthetic cases, not that JSZip+Mammoth as a whole is hardened. Important untested gaps: central-directory corruption/duplicate names/CRC failures, encrypted archives, alternate embedded binaries, XML depth/node exhaustion, parser CPU/deadline termination, malicious entities through alternate encodings, arbitrary relationships, ZIP bombs at realistic boundary sizes, symlink/non-file picker cases, and OS sandboxing. JSZip inflates via library APIs and cannot itself enforce a hard process memory ceiling; the policy must check declared sizes before inflation and run parsing in a cancellable bounded worker/process. No production use is approved by this research.

Fixtures do not cover real-world rendering variation, scanned images, malformed PDF cross-reference tables, non-ASCII font encodings, repeated DOCX header/footer parts, or varied ambiguous role associations. Exact text and simple explicitly labelled category/parent markers are measured; representative automatic mapping quality remains open.

## Resource/security limits (proposals, pending validation)

- Input: picker returns one `.pdf` or `.docx`; validate magic/container and extension; reject mismatch, symlink/non-file, encrypted or malformed input. Copy bytes once into bounded memory; hash captured bytes and never reread the path. Original file is never modified or retained.
- Input bytes max 15 MiB. PDF max 30 pages, extracted text max 500,000 Unicode code points, parse wall limit 5 seconds. Reject encrypted PDF; reject zero-text/scanned-like (<100 non-whitespace chars) rather than OCR. PDF.js worker disabled/network disabled; no embedded JS/actions, attachments, links, launch actions or URL fetches.
- DOCX ZIP max 15 MiB compressed, max 100 entries, max 50 MiB declared/uncompressed total, max 20 MiB per XML part, max 500,000 extracted code points, 5-second parse limit. Reject encrypted ZIP, duplicate/absolute/drive/backslash/`..` paths, unsupported compression, CRC failure, macro-enabled format, DTD/entity declarations, oversized XML/node count/depth, malformed XML, and external relationships; never dereference external targets. Bounds are initial conservative proposals pending resource tests.
- Keep parser process synchronous only under isolated worker/operation cancellation; enforce real wall deadline and terminate worker. Candidate parser must not load remote resources. Cancellation discards preview only.

## Mapping against live profile

Live schema: contact fullName/headline/email/phone/location/named links; categorized skills with optional proficiency/years; experience and projects with nested factual items/technologies; profile entries for education/certificates/summary/languages/extras. Programming languages belong in Skills; spoken languages belong in Languages. Never infer proficiency, years, title/organization, leadership, metrics, employment/training kind, or required-field filler. Preserve unknown passages as unmapped review material.

Structured education dates support `YYYY` or `YYYY-MM`; certificates support year only; experience dates are source-like strings. A finer/ambiguous date remains exact in source evidence, structured date absent, with explicit user resolution or skip. A day-specific source must not be silently rounded. Required items that do not validate remain unresolved/excluded, not invented.

## Provenance, identity, backup

Persist accepted provenance separately from strict profile JSON: source content hash, retained accepted passage/location, owner + exact record/nested-fact id and revision, and field association. App assigns authoritative IDs/revisions. Reimport identical content/passage/owner/revision must deduplicate support independent of temporary proposal IDs. Accepted update retains old-revision provenance history and associates only applicable evidence with the new revision; removal preserves historical references used by drafts; manual edits do not inherit source claims. Profile-only JSON does not contain provenance/history. Version and migrate provenance with complete workspace backup/restore, validate all current/historical references, exclude credentials and unfinished previews; restore sends no requests. No automatic binary retention.
