# Tavily free-only search adapter pilot

This unit adds no Settings field, network activity on key save/status/remove, renderer access, persisted search findings, live provider test, account creation, or paid authorization. The user must create and confirm their own Researcher account and provide a key through a future Settings integration. Search data stays separate from Pi/model credentials and profile data. No API key was available or used in validation.

## Integration boundary

`src/main/research-search-credentials.ts` exports `createResearchSearchCredentials`, `DeviceEncryption`, `ResearchSearchCredentials`, and `SearchCredentialStatus`. Main must pass Electron `safeStorage` as the injected encryption implementation, a real `app.getPath('userData')` directory, and the workspace directory. Do not pass a path inside a workspace or any workspace backup. The service writes only an encrypted file under `userData/private-auth/tavily-key.dpapi`, using a private temporary file, sync, then atomic rename. Encryption unavailable means no write or plaintext fallback. Status exposes only `configured`, `storageAvailable`, and a fixed message. Removal deletes the local key, not the provider-side credential. Errors never include a key or provider response. `withKey` is strictly a privileged main-process callback and must never be wired to IPC or to a renderer. Encrypting bytes is delegated to Windows Electron safeStorage and is not tested on a live installation in this unit.

`src/main/tavily-search.ts` exports `createTavilyResearchSession`, `PublicJobSearch`, `TavilySearchResult`, `TavilyLink`, and `TavilyTransport` for injected Node tests. The future orchestrator must check that metadata is public, that the posting identity or employer domain is verified, and that the user explicitly initiated a fresh run before constructing a session. Typed input accepts only role title, posting host, optional canonical role ID, or a verified employer domain and optional title. It cannot accept arbitrary provider options. It must never pass profile/CV text, Pi keys, private URLs, or contact identifiers disguised as a title. This adapter rejects obvious email/control data, but cannot itself prove a title is publicly sourced. Candidate result URLs still need the orchestrator's source normalization, identity check, safety validation, review and rights clearance; snippets alone are partial, not role facts.

A session reserves at most three searches synchronously, serializes preflight and search, and sends at most five links per query. Each search performs a bounded authenticated `GET /usage` preflight, then exactly one `POST /search` when the response unambiguously reports `Researcher`, plan limit `1000`, zero pay-as-you-go usage and limit, and at least one credit remaining on both account and key. Unknown or altered plan metadata is refused. All requests use fixed HTTPS `api.tavily.com`, public DNS validation, pinned IP with hostname TLS verification, no redirects, a 12-second per-request deadline, a 256 KiB response limit, no retries and generic errors. Only these fixed fields are sent: `search_depth: basic`, `auto_parameters: false`, `include_answer: false`, `include_raw_content: false`, `max_results: 5`, `chunks_per_source: 1`, `topic: general`, `include_usage: true`. It returns only bounded HTTPS URL candidates, titles, snippets, credit count and request ID; it drops the AI answer, raw page content and the rest of the provider payload. A malformed response, DNS pivot, wrong credit count, timeout or cancellation produces no evidence. The API key is supplied only as the Authorization bearer header to the fixed Tavily host.

## Published facts and gate limits

The [Search API reference](https://docs.tavily.com/documentation/api-reference/endpoint/search) describes `POST /search`, basic search at one credit, request fields, response usage and request ID. The [Usage API reference](https://docs.tavily.com/documentation/api-reference/endpoint/usage) documents `GET /usage` with `account.current_plan`, `plan_usage`, `plan_limit`, `paygo_usage`, `paygo_limit`, and key usage/limit. The documentation shows `Bootstrap` as an example but does not enumerate permitted `current_plan` strings or guarantee that a free account returns exactly `Researcher` and zero paygo limit. This adapter therefore fails closed if actual free-account responses differ. An operator must confirm the actual plan and paygo metadata through their own Tavily account before enabling this pilot. Do not loosen the check to infer a tier from key prefix. The [pricing page](https://www.tavily.com/pricing) lists free Researcher at 1,000 monthly credits with no card and says requests stop after exhaustion unless upgraded; paid plans and pay-as-you-go can bill normally. This adapter cannot independently guarantee the account remains on a free tier between the preflight and POST, or account-wide concurrency from other clients. Integration must not offer paid use implicitly. The app never upgrades or subscribes.

The [privacy policy](https://www.tavily.com/privacy) says queries can be retained, used to improve service and sent to other search-index providers. [Terms](https://www.tavily.com/terms) do not grant blanket rights to store third-party full-page content. Before persisting anything in jobs or backups, obtain permission for brief attributed excerpts and the relevant direct-source text. Do not persist full provider responses. Keep company context distinct from role requirements and require explicit outgoing-data review before any separate Pi analysis.

## Verification

Run targeted Node-only mocks, with this worktree's isolated `.audit/vitest.tavily.config.mts`, using `./node_modules/.bin/vitest run --config .audit/vitest.tavily.config.mts --maxWorkers=1`. Typecheck with `./node_modules/.bin/tsc --noEmit --pretty false`. No installed Electron, real DPAPI, Tavily request, package build, native rebuild, or full suite was run. The `.audit` test config and cache are private to this worktree and not committed.

Model the Domain made a session own the three-dispatch counter and serialization, rather than spreading accounting across callers. Boundary Discipline put strict provider, DNS, encryption, and JSON checks at main-process boundaries; downstream orchestration still owns source identity and user consent.
