# Issue 102: unmodified Pi Web Access under strict Windows isolation

**Decision: STOP / deferred negative feasibility for unmodified `pi-web-access@0.44.0`.** This is a read-only integration assessment, not an OS/network test of Pi Web Access and not proof that a maintained fork is impossible. The maintainer keeps strict OS process/network isolation for any future Pi Web Access child and chose a separate trusted-main-process **Lever/Greenhouse exact-posting API** route instead of weakening that boundary. No Pi Web Access child or production web intake was enabled.

The installed package exposes a standalone stdio MCP CLI (`dist/mcp-cli.js`) and a Pi extension. The inspected MCP tool dispatch calls the package's own provider search/fetch paths, which make HTTP requests. Its documented HTTP(S)/SOCKS proxy and provider-base-URL settings are network routes, not a typed named-pipe callback that lets an OS-denied-network child request only an approved named-posting operation from a parent. No supported provider transport injection seam was identified in the inspected `0.44.0` CLI, package metadata or README. A general proxy would undo the intended egress boundary. If the parent performs all fetching and merely hands results to a child, the unmodified package is not supplying meaningful provider functionality. A deliberately maintained transport fork could be investigated separately; the assessment does not rule it out.

Do not conflate caches: the Pi **extension** documents a private disk cache with one-hour TTL (128 entries / 128 MiB); `PI_WEB_ACCESS_CACHE_ROOT` relocates it rather than disabling it. The standalone **MCP** path retains up to 50 result IDs in process memory and loses them on exit in the inspected route. That is not a guarantee that optional GitHub clone, PDF, browser-cookie, command credential, or other capabilities cannot touch disk when enabled. Many private-file and credential features are conditional, not mandatory for every provider, and an app-owned restricted config/scratch root might narrow them. Such a root still cannot supply live provider responses to a child that the OS forbids from making network requests.

Earlier #102 MCP lifecycle experiments remain unverified for child reaping, response bounds and cleanup. The physical dependency check does not validate app packaging. The [fixed atomic AppContainer+Job child observation](https://github.com/MakCoder-2004/ATS-CV-Creator/issues/102#issuecomment-6423860651) verifies only one normal-path system binary launch, token/job identity, exit and owned profile cleanup. It does **not** validate package/file access, provider egress denial, named-pipe broker, forced-parent recovery, or installed-app behavior. The [issue 95 prototype](issue-95-pi-web-access-prototype.md) had already deferred direct integration without those gates.

**If this path is reopened:** use a supported upstream transport hook or a maintained fork with an exact typed broker protocol over non-network IPC. The child must have no direct network or host-private-file access; all provider and secondary outbound paths must fail closed unless the parent validates destination, method, selected role, redirects, response size, timing and run authorization. Disable unused local-file, cookie, GitHub, media and command-credential capabilities; prove scratch/cache ownership and deletion on cancellation, crash and restart, package layout, and installed Windows operation. No broad proxy, access-control bypass, or implicit paid provider is approved. A new issue/review and separate OS-execution approval are required before treating this deferred research as integration permission.

**Separate route chosen:** The maintainer's [personal-local Lever/Greenhouse policy](https://github.com/MakCoder-2004/ATS-CV-Creator/blob/main/docs/decisions/personal-local-posting-source-policy.md) allows future, narrowly allowlisted named-job API adapters in the **trusted main process**, not a Pi Web Access child. This changes #93/#98 implementation scope and does not claim that main-process fetches have the same OS isolation as an AppContainer. #97–#99 must still prove exact-role matching, SSRF/redirect/DNS bounds, explicit review/save, temporary data cleanup, backup disclosure, and paused-host regression behavior. #104's existing source pause remains until those adapters are accepted. Manual paste stays available; #101 installed validation needs separate approval.
