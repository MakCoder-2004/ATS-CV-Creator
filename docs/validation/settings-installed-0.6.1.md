A standalone Electron path probe showed that `--user-data-dir` isolates `app.getPath('userData')`, while changing the child process's `APPDATA` does **not** isolate `app.getPath('appData')` on this Windows installation. The production encrypted Tavily key belongs under `appData`, outside the SQLite workspace. Proceeding past the guard with a synthetic key would risk overwriting a real device key. Therefore the stopped harness is a **safety refusal, not a passed installed key test**. The user chose to check the installed key controls manually rather than let an agent touch the real key store. Their observation is pending; manual Reveal/Hide/Copy and Cancel must not be reported as passed before they confirm them. They should never share the key contents, should clear the OS clipboard (and clipboard history if enabled) after Copy, and should not choose **Revoke locally** unless they intend to delete the saved device copy. Synthetic installed revoke/DPAPI persistence still requires a separate Windows user profile or a new explicit, safely scoped plan; do not weaken the guard or silently use the user's key store. Opening Settings for the read-only layout smoke may check key *status* but did not decrypt or modify a key. The actual user's default SQLite workspace was not used for these checks.
