# Volatile researched findings session (Wave 2A)

This is a bounded integration unit for issue #88, **not a shipped end-to-end research workflow**. Main-process `job-research:start/get/search/review/cancel` are distinct from the legacy saved-job posting import. `src/main/job-research-session.ts` holds at most five research tokens for 15 minutes, cancels old/expired work and rejects late completions. Runs and reviews have no job ID, SQLite writes, analysis cache, workspace backup, or recovery path. Returned runs are copies of immutable app-held records; review uses app-issued finding IDs and verifies references and evidence hashes against the held run. Nothing in this unit sends evidence to Pi or creates a saved job.

A start action performs one bounded direct public read. The search method is a **separate explicit action**, only allowed when that read is incomplete and only once per token (including a failed search to prevent hidden repeat charges). It checks encrypted device-only key status then uses `createTavilyResearchSession` with free-Researcher `/usage` verification, one basic role query, five-result maximum and no answer/raw content. Query contains the selected canonical host and exact role ID where available, never title scraped from pages, CV/profile/contact details, URL parameters or long untrusted keywords. If no ID, query contains only the selected host. One role search is deliberately below the ceiling of two role queries and one verified-employer query; employer search is withheld because the current direct adapter does not yet furnish an authoritative employer-domain link. Search may expose public query terms and the user's network metadata to Tavily and its index providers; the renderer must disclose this before the button is made available. No account, key, live call, paid tier or plan upgrade was configured in this work.

Search result URLs are untrusted leads. A lead must normalize to the **exact selected canonical URL** (including the path for generic URLs without IDs), have a meaningful title and a nonempty excerpt; another role ID or a namesake link does not qualify. Only the selected canonical URL may receive one bounded, DNS-pinned direct re-read; search-provided URLs are never fetched. A fresh *full* direct read takes precedence without an indexed excerpt. Fresh partial direct evidence is preserved alongside the original direct capture; indexed titles must equal the normalized direct title **exactly** after removing only a suffix naming the directly verified employer (`—`, `–`, `-`, `|`, or `at`). Normalization retains Unicode letters and numbers (NFKC plus case folding) so non-Latin title and employer identity words cannot disappear; extra seniority or another employer is a conflict even with the exact URL. If no direct role metadata exists, a URL-only lead keeps its explicit identity caveat and no verified employer. A blocked or empty re-read authorizes an indexed **partial** fallback only when the direct adapter explicitly tags it `accessFailure: 'unreadable'` (for example, a same-host HTTPS login gate, HTTP 401/403 or an identity-matched HTML page lacking readable posting text); HTTP 404/410 are tagged `removed`, HTTP 5xx `server-error`, and unexpected statuses including 429 are unsafe. None authorizes indexed fallback, including when an earlier direct read was partial; unknown/untagged historical outcomes fail closed. Private DNS, TLS/transport errors, different-host/role redirects, invalid/tracking redirects and loops never authorize fallback; unknown thrown errors also fail closed without revealing transport details. An initial partial direct capture is retained when follow-up reads fail, without accepting the indexed excerpt. A fresh *full* direct read still takes precedence. No matching indexed lead means no new claim. Snippets never become full postings or verified employer context. Results and reviews remain memory-only pending source and Tavily rights clearance.

The Wave 2B/renderer integration must show full/provisional/none/blocked, sources and unknowns; add distinct Outgoing-data consent and a persistence-free analysis route if provisional Pi analysis is enabled. Do not call `saveJob`, `startAnalysis` for saved jobs, or generate a draft from these tokens. The existing direct-full saved-job intake and Lever legacy path remain unchanged. Settings UI and credential IPC are separate work. No packaged app was launched; existing 0.5 remains untouched. For integration, check preload compatibility: `src/shared/job-research.ts` currently imports Node crypto/util and is transitively imported by renderer via `posting-identity.ts`; an Electron/Vite renderer build fails on its Node builtins. Core owner/root should move hash/verification behind the main-only boundary or split pure schemas/normalizer from crypto before final build.
