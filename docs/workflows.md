# Implemented workflows

This page describes the current Pi-powered source code and the [installed 0.4.0 validation](validation/pi-sdk-installed-0.4.0.md). Earlier 0.3.0 validation reports remain historical evidence for the former OpenRouter release. This is a reference for product changes, not a description of the browser-only prototype or a plan for future job discovery. The [architecture map](architecture.md) identifies the code that owns each boundary.

## Prepare a tailored CV

The Tailor CV page moves through five stages in [`WorkbenchStart.tsx`](../src/renderer/WorkbenchStart.tsx) and [`WorkbenchStageLayout.tsx`](../src/renderer/WorkbenchStageLayout.tsx).

1. **Job posting.** Select a saved job or add one in Saved jobs. The accepted working posting, not a separate captured source snapshot, is the input for assessment.
2. **Outgoing data.** Inspect the exact minimized posting and profile facts, the destination, selected Pi model and thinking level, and the privacy notice. **Include a cover letter** starts unchecked; changing it replaces the preview and requires explicit authorization of the new CV-only or CV-and-letter purpose. The single **Authorize and start this run** action records one-run consent and starts posting analysis. An analysis failure offers an explicit retry. Neither an older cache entry nor a prior approval authorizes a new run.
3. **Generate.** Read the analyzed required and preferred qualifications, tools, responsibilities, and keywords. Choose a one- or two-page target, then explicitly generate. The application selects profile evidence and asks the model for structured, cited wording and, only when supported, an optional concise CV title tailored to the posting without copying its title or inventing seniority. New experience and project descriptions are one paragraph, with no more than 60 words. Existing drafts without explicit format metadata keep their released bullet layout. One long saved fact can still supply a section when its source exceeds that section's estimated output length. The app measures actual PDF page fit later. Generation progress reflects recorded work. A received malformed response saves no model wording and cannot be resumed; review outgoing data before explicitly starting another run. A structured response with invalid citations is discarded and leaves an empty, blocked draft for source-backed manual correction. A current-format interrupted run with an uncertain request needs an explicit retry decision. Earlier prompt-format recovery snapshots (versions 1 through 4), including Pi snapshot version 2, cannot resume under old consent; they remain readable and need a fresh preview, consent, analysis, and generation.
4. **Review evidence.** Inspect the optional AI-suggested CV title beneath your name. Edit or remove an existing title for this CV only through **Edit CV title** in the document toolbar. A title change requires renewed checks, PDF fit and approval. Select wording to see its linked source and inclusion reason immediately beneath it in the review-only paper; dismiss that context without changing the CV. The readable Review details panel keeps the three views Sources, New skills and Job match beside the document when space permits, or opens as a requested dialog when it does not. The Checks & options panel and its advanced AI wording/title-regeneration tools have been removed. The separate Check CV for issues button is removed. Check page length runs the local factual checks and measures the actual PDF without a model request; approval remains gated. Review issues opens a compact finding list. Correct wording through Sources or add/edit complete records directly in the CV. Posting-only skill suggestions are marked **Not in your profile**. Confirm or remove each suggestion before approval. Confirmation applies to this CV only and does not establish past work with the tool. Edit wording or add and remove records using selected evidence, run factual checks, measure the actual PDF page fit, resolve findings, and acknowledge the current wording before approval. A proposed page cut changes the draft only after acceptance and clears the prior checks and approval.
5. **Export.** Review the actual compiled PDF. Export the approved content as a selectable PDF or editable DOCX. The DOCX uses the same canonical content but can paginate differently. A draft edit, changed source, or changed posting can require renewed review before export.

The PDF uses Letter paper and Lato, with Education, Experience, Projects, and grouped Technical Skills. New and explicitly regenerated experience or project descriptions render as paragraphs in review, PDF, and DOCX. The PDF leaves readable leading between heading metadata and prose. Project links remain clickable and right-aligned in the same heading row; paragraph-format project headings use a bounded wrapping link column so long repository labels do not collide with titles or technologies. Older drafts without format metadata retain bullets, including unchanged siblings grouped under the same role or project as a newly regenerated paragraph. Their canonical content hashes remain unchanged. Education places school and dates on the first row, degree and any supported GPA/CGPA on the second; repeated metadata in generated wording is omitted from education descriptions without changing saved profile facts. It has no narrative summary, verbatim posting-title headline, or Certificates section; an optional cited professional title can appear beneath the name. Profile facts remain in the profile even when a section is omitted from a particular CV. The model does not write LaTeX. Evidence and deterministic checks support review but do not prove that a statement is true or that a CV will pass an ATS.

## Enter and manage a saved job

[`SavedJobs.tsx`](../src/renderer/SavedJobs.tsx) uses manual-only intake: enter a title, company, and complete job-posting text, then explicitly save it to the local workspace. There is no active URL field, fetch/research/search route, refresh action, named-host adapter, or Open original job action. Opening or editing a saved job makes no job-host request. Existing posting source snapshots, URL provenance, accepted revisions, drafts, approvals, and backups remain available and are never rewritten by this pivot; historical URLs are inert, read-only provenance.

Contacts may be manually added repeatedly to the current saved-job record (bounded name, role label, optional HTTPS profile URL). Contact-only saves do not add posting revisions or change the accepted posting timestamp. Contacts are excluded from outgoing model data and generated CVs. An explicit profile action opens a public HTTPS address in the default browser; localhost/private/intranet hosts are rejected. On the explicit profile action the app performs only a DNS public-address safety check; it sends no profile HTTP request, does not pin the browser's later DNS resolution, and cannot inspect redirects. The default browser owns final navigation. The app does not discover, enrich, or message contacts.

The Saved jobs table retains its Posting, Draft status, and Next action columns, with Open posting, Edit, and Delete actions. Company appears beside the title on the first row when space permits; long names wrap within the Posting cell without shifting status or actions. Deletion preview/confirmation and transactional cleanup remain unchanged; profile facts and exported files are not deletion targets, while older backups may still contain deleted jobs. Source URL history is displayed only as inert text.

The previous link, research, and named-source route behavior survives only as dated validation/history. It is superseded by issue #116 and is not a current feature contract.

## Maintain a profile

[`ProfileEditor.tsx`](../src/renderer/ProfileEditor.tsx) edits contact information, skills, education, certificates, summary, languages, and other facts. Experience and projects use their own record editors. The profile records facts for future drafts; CV-only edits do not silently rewrite it. Manual draft-record operations can explicitly target the CV alone or both the CV and profile, with source history retained. Editing an existing experience or project record keeps its paragraph format when the selected draft item has one, in either scope. Manual descriptions can exceed the 60-word limit for model-generated paragraphs, but the edit clears prior fit and approval and still requires review. Older items without format metadata keep their bullet layout. A new factual assertion requires current saved evidence; declaring a wording-only change is not a truth guarantee.

PDF and DOCX uploads create temporary profile proposals; they do not change saved facts. The existing importer reads each document locally and keeps the local proposal route available. AI-assisted extraction is the primary presentation, with **Continue locally** as a clear alternative. Before any provider request, the app shows the minimized readable source text, selected Pi provider, model and thinking level. One **Authorize and structure CV** action authorizes and starts the request after the person can inspect that preview. The optional exact-text disclosure remains available. The app sends no binary document, saved profile, unrelated file or credential. It gives the model complete application-issued page and passage references, including text the local mapper did not classify. The app accepts only exact cited source passages, assigns proposal identities itself and leaves uncertain role types or unrepresented text unresolved for review. It rejects AI output that drops explicitly supported local facts rather than replacing the review with fewer facts. A new role can be classified as Employment or Training only when its own cited parent passage explicitly labels the kind and contains both its title and organization. A PDF line or DOCX paragraph can contain more than one role heading; its authentic source locator does not establish which role owns each field. AI proposals citing such a unit are rejected without replacing the local review, where the original text remains inspectable. A heuristic local role kind can be corrected only when the same parent passage supplies a clear contrary label, including an `Internship — organization` role heading. Incidental description words and another role's label do not establish its kind. Source-backed skill categories stay unchanged unless the skill's own cited passage has one unambiguous heading for a different supported category. Multiple skill headings in one source unit cannot authorize a category change or a new skill classification; unchanged locally sourced categories remain proposals for review. Certificate and project links need their own cited URL or attached hyperlink. AI output remains editable proposals. The person reviews add, update and skip choices before atomic application. A stale profile leaves the temporary review available for an explicit refresh of merge choices; corrections to record kind preserve the original source passage without treating other manual wording changes as source support. Profile JSON export and import remain a separate exchange and replacement flow. These paths are implemented in [`src/main/profile-pdf-import-ipc.ts`](../src/main/profile-pdf-import-ipc.ts), [`src/main/profile-docx-import-ipc.ts`](../src/main/profile-docx-import-ipc.ts), [`src/shared/profile-source-evidence.ts`](../src/shared/profile-source-evidence.ts), [`src/shared/profile-ai-structuring.ts`](../src/shared/profile-ai-structuring.ts), and [`src/main/profile-exchange-ipc.ts`](../src/main/profile-exchange-ipc.ts).

## Manage settings and backups

Settings stores appearance, one exact Pi provider/model and thinking level. Choose an available model and sign in with Pi outside CV Tailor. The Pi model card includes external sign-in guidance; there is no separate Provider sign-in or Optional faithfulness review card, in-app Pi provider key or local model-usage budget. Indexed search is retired for all hosts. Settings shows no search UI when there is no encrypted legacy key. If an old encrypted Tavily key remains on another installation, Settings offers only explicit confirmed local removal; it never reveals, copies, saves, replaces, or uses the key. Removal affects this device only and does not revoke the key in the Tavily account. A failed status check does not imply absence, and upgrades/backups do not silently delete the credential. No Settings action initiates search or stores standing model consent. Saved postings are entered manually; no job-link fetch, public research, or URL action is available. Inspect Outgoing data and authorize each CV-tailoring run explicitly. Removing an old key affects only the device copy. The approved upgrade deletes CV Tailor's old encrypted OpenRouter key row and the retired faithfulness setting, not Pi's credentials. Older `semantic-unsupported` findings stay attached to saved drafts; paused runs from the earlier review contract require a fresh outgoing-data review and authorization. Each new model run needs an outgoing-data preview and consent, including when saved analysis is reused. [`PiSettings.tsx`](../src/renderer/PiSettings.tsx), [`LegacySearchKeyCleanup.tsx`](../src/renderer/LegacySearchKeyCleanup.tsx), [`research-search-settings-ipc.ts`](../src/main/research-search-settings-ipc.ts) and [`workbench.ts`](../src/main/workbench.ts) own these controls.

[`WorkspaceBackup.tsx`](../src/renderer/WorkspaceBackup.tsx) exports the local workspace. Restore previews the replacement, validates known records, makes a safety copy, and then reopens the workspace. A backup excludes credentials. Restoring an older backup drops OpenRouter model and budget settings; restored consent cannot authorize new Pi work. Saved drafts and source history remain readable. A pre-Pi generation run remains visible as unable to resume; any unsettled provider attempt count remains visible without permitting replay. The application's backup path is the supported restore operation; a raw SQLite file copy is not.

## Optional cover letter

The production Tailor CV renderer connects the optional letter to the same five stages. Initial authorization still starts only posting analysis; **Generate tailored draft** is a separate decision and generates the requested documents. A letter failure or cancellation does not remove the saved CV. A structurally valid letter that passes privacy and citation-identity validation is saved for editing even when its factual checks find unsupported skills, numbers or attribution. Those findings stay visible and block approval/export until corrected. Malformed output, foreign citation ordinals and detected unauthorized identifiers are still discarded. The authorized purpose remains visible in Generate. The letter request asks for three concise, professional and friendly paragraphs centered on relevant experience, not a technical inventory: a warm opening, a high-level work/project summary and a short closing. It allows at most two relevant named tools, omits routine grades/study details and does not infer a completed degree. Education/skill source records appear as readable text in the request and review, while their frozen original passages remain unchanged for provenance.

Inside Review evidence and Export, the **CV / Cover letter** selector keeps their review and approval independent. Letter review shows actual linked source passages, local paragraph editing, a recipient-name field (never sent to Pi), separate paragraph acknowledgments, current factual findings, actual compiled one-page fit, and explicit letter approval. Recipient and body edits do not write to the CV or profile and require renewed letter review. Latest generation status and retained-document readiness are shown separately: an older letter can remain available after a later failed attempt. New failed attempts retain only a fixed diagnostic category, not rejected prose, so their specific failure explanation survives reopening. The frozen letter origin, not a newer CV revision or retry attempt, supplies its source context.

Approved-letter Export displays its real compiled PDF with separate **Export cover letter PDF** and **Export cover letter Word** native-destination actions. Word may reflow. **Back to review** does not itself revoke approval; edits do. Current main-owned readiness gates export, not a raw stored approval flag.

Where main permits it, **Review data to add/regenerate a cover letter** prepares fresh letter-only consent, including any earlier-charge uncertainty warning. After explicit acceptance, **Generate cover letter** is a separate pause: it does not analyze again or regenerate the CV. If bindings do not allow this bounded retry, the UI explains the need for a fresh full flow. Local recipient selection is retained by the backend for the same job. Job visits and read requests are fenced so earlier responses do not appear under another posting, including A → B → A navigation.

See the [artifact-controller API](validation/cover-letter-artifact-integration.md), [renderer validation boundary](validation/cover-letter-visible-flow.md), and latest [editable-letter findings check](validation/editable-cover-letter-findings.md). The validation report records the earlier focused real-main Electron success using synthetic provider responses. It is not live-provider, packaged, or installed acceptance; later UI and diagnostic changes have their own scoped checks.
