# Job-posting source access and retention gates

**Research date:** 2026-10-26. **Purpose:** Set source-specific gates for automatic retrieval and saved job postings. This is documentary research, not legal advice or an authorization to fetch, display, use, or retain any source content. A later [personal-local maintainer policy](../decisions/personal-local-posting-source-policy.md) conditionally accepts Lever and Greenhouse for the maintainer's own future workflow without claiming the platforms granted new rights; the shipped source pause remains in force.

## Decision

No reviewed source has both an authorized automatic retrieval route and established rights for durable display/use and retention in CV Tailor. Do not enable automatic saving or refresh for any newly fetched source based on this report. LinkedIn is **BLOCKED**. Indeed is **BLOCKED**. Greenhouse and Lever are **INCONCLUSIVE** because their official technical documentation describes public read routes but the reviewed official materials do not settle this app's downstream display, use, storage, and deletion rights.

A reachable URL, public endpoint, or user's Save action does not grant reuse rights. Manual paste is a separate user-authored route, not automatic source capture and not evidence that fetched wording may be saved.

## Status meanings

- **ENABLED** means the reviewed official terms and documentation support the stated automatic route and its specific downstream use and retention.
- **BLOCKED** means reviewed official terms rule out the proposed route or no permitted route is documented for this use.
- **INCONCLUSIVE** means a technical route exists or may exist, but official evidence reviewed here does not resolve authority for this app's use. Treat it as unavailable until the gate is resolved.

The automatic retrieval verdict is about permission and approved scope, not whether an HTTP request might return a response. The separate save/retention verdict covers keeping source wording as a posting source snapshot and displaying or using that wording in a saved job and CV-tailoring workflow.

### What the technical documents do and do not establish

Greenhouse and Lever document narrowly addressable public reads. Their endpoint shape, response fields, and unauthenticated access do not establish a license for storing a captured posting or using its text as durable CV-tailoring input. Conversely, the absence of a retention clause in these API documents is not permission for indefinite storage. LinkedIn restricts scraping and approval-dependent API data storage. Indeed's site rules restrict automated access outside an express permission or the narrow `robots.txt` crawling exception; its developer agreement separately limits approved API integrations.

No claims here rely on search-result summaries. The cited official pages were reviewed directly on 2026-10-26. Page revision dates are included where the pages state them. No live posting URL, login, cookie, authenticated session, or posting body was accessed.

## Manual paste is separate

The current app accepts manually entered job-posting text and saves it on device. That path is a user's own entry, not automatic source capture. Pasting does not make a source fetch permissible, prove the pasted text is authorized for any use, or turn an unaccepted fetched preview into a saved posting. Keep the two paths clearly distinguished in product copy and storage decisions.

## Conditions for any future accepted source

As CV Tailor's product signoff policy, a source can move to **ENABLED** only after its applicable official terms or a written permission/agreement establish the named route, selected-job scope, full-text retrieval, display to the user, use as input to CV tailoring, and storage in the workspace and backups. This is a conservative release condition, not a claim that every public endpoint legally requires a separate written license. Record the applicable account, approval, API scope, permitted fields, frequency or rate limits, attribution, and any charges. Re-review if the integration, source terms, data use, or storage policy changes.

If a source passes that gate, each posting source snapshot must retain provenance separate from the user's working posting and corrections. Store the canonical source URL, provider and route, source posting ID, retrieval timestamp, source-reported update/publication dates when supplied, parser/version, and content hash. Display retrieval time and source identity. Refresh only on explicit user action through the same approved route. Never label captured text current solely because it was once fetched. Let users inspect captured wording against their working posting and accept or reject corrections without rewriting the snapshot.

Before enabling a source, define its expiration and deletion rules, including how deleting or expiring a saved job handles its snapshot, working posting, revisions, derived data, and older backups. A user's Save action is not a substitute for those rules. A source-owner request, license end, or access revocation must follow the applicable terms; a user's correction alone can keep the immutable source snapshot unless those terms or an explicit product rule require removal. Specify backup expiry or rewrite, restore behavior, and any permitted audit-only receipt. These are proposed product obligations, not claims that today's delete erases old backups: current backups can restore deleted jobs. Retention duration, backup treatment, and any exception must be explicit before implementation.

## Product gate and current UI conflict

Until one source passes both gates, new automatic capture may be reviewed only as temporary content if separate temporary-access and cache rules authorize it. Do not enable a new saved or refreshed posting source based on successful fetch, public reachability, or consent to save. If all sources remain unresolved, offer manual paste and do not promise saved automatic intake. This report does not itself turn off an existing feature.

The current [Saved jobs UI](../../src/renderer/SavedJobs.tsx) says “LinkedIn, Indeed, Lever and other public HTTPS job links may work” and allows a direct-fetch path for non-Lever sources. That copy suggests general availability and conflicts with these rights gates. The current [workflow guide](../workflows.md) says new non-Lever fetches are temporary and cannot be saved, while Lever retains a save/refresh path. The shipped Lever fetch, save, refresh, source history, and backups are a present unresolved disposition, not a route newly approved by this research. The earlier three-request user waiver covered bounded feasibility checks, not production retention. A maintainer must now record whether to retain the existing Lever behavior under an explicit scoped product and legal risk decision or authorize a separate pause with migration and backup implications. An absence of an express reuse grant is not proof of a blanket legal ban and does not justify an unreviewed shutdown. This research task makes no code or copy change. The UI's source-availability claim also needs correction before any broader intake release.

## Evidence limits

This review covers the official sources linked above and prior project findings. It does not decide copyright, contract enforceability, or whether a particular user has rights to a pasted posting. It does not review every country-specific term, employer agreement, API contract, or downstream rightsholder. Under the product signoff policy above, seek source-specific permission or an applicable agreement and record the maintainer's decision where the documents leave reuse and retention unresolved.
