## Executive summary

This is a substantial **local-first, prompt-orchestrated job-search framework**, not a standalone web app or a fully automated application bot. Most lifecycle features are detailed Markdown instructions interpreted by Claude Code (with limited portable Agent Skills support for the portal CLIs). The genuinely executable integrations are mainly portal-search CLIs, helper/validation scripts, salary-data lookup and PDF verification. Application drafting, fit reasoning, company research, interviews, skill-gap analysis, email classification, and Notion operations depend on an LLM runtime and—in some cases—optional MCP connectors, external tools, or user-supplied data. Human approval gates are central; the documented workflow does not submit applications or send outreach automatically.

The repository is unusually explicit about boundaries and data contracts, but its privacy documentation contains a material contradiction: SECURITY says the populated profile is gitignored, while the README says `/setup` writes personal details into tracked files, and the checked-in `.gitignore` does not ignore `CLAUDE.md` or `.claude/skills/job-application-assistant/01-candidate-profile.md`. Do not assume profile privacy from the gitignore. Other practical caveats: Claude Code subscription/API is the primary runtime, built-in portal coverage is Denmark-focused plus LinkedIn/freehire, LinkedIn automation is expressly personal-use-only/ToS-risky, LaTeX plus PDF parsing tools are prerequisites for full document verification, and several advertised features are workflows/specifications rather than shipped integrations.

## Workflow/data structures

- **Candidate source of truth:** `CLAUDE.md`, `.claude/skills/job-application-assistant/01-candidate-profile.md` and companion methodology files. `AGENTS.md` calls the cross-runtime strategy a thin pointer into canonical `.claude/` specs, avoiding duplicate prompt trees ([AGENTS.md](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/AGENTS.md#L9-L19)). The behavioral assessment and writing voice are separate profile/spec inputs ([behavioral profile](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.claude/skills/job-application-assistant/02-behavioral-profile.md#L10-L54); [writing-style guide](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.claude/skills/job-application-assistant/03-writing-style.md#L7-L24)).
- **Scraper state:** `job_scraper/seen_jobs.json` is a `seen` object keyed by canonical posting key, with title/company/url, first-seen and posted/deadline dates, fit/status, portal and source. `/rank` adds scores/verdict/date, veto fields and strengths/gaps. Missing/null dates must not be guessed. Schema is documented in [job-scraper spec](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.claude/skills/job-scraper/SKILL.md#L152-L180).
- **Applications:** `job_search_tracker.csv` tracks lifecycle, channel, score and file paths; `documents/applications/<company>_<role>/` stores the posting, submitted documents, `outcome.md` with dated notes and interview-stage checkboxes. Exact status vocabularies are defined in [outcome spec](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.claude/commands/outcome.md#L48-L62), and archive format follows [Step 3](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.claude/commands/outcome.md#L160-L187).
- **Salary data:** JSON with optional metadata baseline/label and company entries containing optional city and category count/index values; dataset file is ignored/personal and user-maintained ([executable](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/salary_lookup.py#L20-L28), [format usage](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/salary_lookup.py#L49-L102)).
- **Company cache:** `company_research/<normalized-name>.json` has fetch date, URL+notes by research area and a network-contact note; cache TTL is 30 days and claims are re-verified ([schema and rules](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.claude/skills/job-application-assistant/04-job-evaluation.md#L182-L227)).
- **Extensions:** portal skills use a documented `search`/`detail` JSON/table/plain contract; `/add-portal` scaffolds a new prompt/CLI skill after a test search; `/add-template` registers custom document toolchains. These “generators” are agent instructions, not a conventional plugin manager. The README describes the customizations; contributor policy explicitly says market-specific additions and other runtime ports generally belong in forks ([README extensions](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/README.md#L275-L344); [contribution scope](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/CONTRIBUTING.md#L1-L28)).

## Safety, privacy and external dependencies

- **Privacy claims are contradictory; do not assume profile files are protected by gitignore.** SECURITY claims a populated profile is gitignored and says documents never leave the machine by design. At this pinned snapshot, README explicitly says `/setup` writes personal details (name, contact details, employment history, salary expectations) into **tracked** files; `.gitignore` does not ignore root `CLAUDE.md` or `.claude/skills/job-application-assistant/01-candidate-profile.md`. It ignores the tracker, salary JSON, generated outputs, and documents subfolders, but those exclusions do not protect the tracked profile files. Thus an ordinary public GitHub fork can expose personal profile data; the README itself directs personal users to create a private repository instead of a public fork. Do not characterize the populated profile as gitignored or safely local based on SECURITY alone ([README fork/privacy warning](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/README.md#L81-L88); [actual ignore rules](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.gitignore#L22-L32), [generated data exclusions](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.gitignore#L59-L112); [contradictory SECURITY statement](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/SECURITY.md#L11-L17)). Separately, “documents never leave the machine” is an upstream design assertion, not established data-flow evidence: `/setup` and `/apply` direct the LLM to read/process CV/profile contents. With the documented Claude Code hosted model, content sent to the model is outside the local filesystem; provider routing, retention and processing terms were not audited here. `/notion-sync` specifies filenames only, but `/gmail-sync` reads message bodies through the connected Gmail service. The repo is explicit that untrusted postings and personal data share an agentic context and prompt rules are not a sandbox.
- **Model/runtime dependence:** Claude Code is the primary supported runtime, requiring paid subscription or Anthropic API credits per README. Agent orchestration, web search/fetch, profile reasoning and generation are not vendor-neutral executable code. Some portal CLIs can be discovered by other runtimes through `AGENTS.md` and portable `SKILL.md`, but that does not port the full application workflow ([README prerequisites](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/README.md#L62-L68); [runtime policy](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/CONTRIBUTING.md#L53-L69)).
- **Integrations are optional/user-authenticated:** Notion MCP/OAuth and Gmail MCP are not included services; without configured tools those commands stop. LaTeX distribution is needed for CV/letter outputs. pypdf or Poppler enables ATS extraction; no parser means degraded visual/manual review. Bun and Python are needed by search tools/setup scripts ([README prerequisites](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/README.md#L62-L68); [Gmail preflight](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.claude/commands/gmail-sync.md#L11-L15); [Notion preflight](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/.claude/commands/notion-sync.md#L26-L35)).
- **Scraping/legal:** LinkedIn uses public unauthenticated endpoints and is flagged as personal-use-only because automated access violates its Terms of Service; the README advises low volume. Danish portals and public job data can change, block clients or restrict reuse. `robots.txt` gating, retry/backoff, bounded checks and portal health guidance improve care but do not grant terms-of-service permission. Community-contributed skills are explicitly outside upstream security policy and must be reviewed ([README LinkedIn caveat](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/README.md#L287-L305); [SECURITY scope](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/SECURITY.md#L19-L21)).
- **No automatic external action:** Networking is link generation only; applications, follow-ups and thank-you messages are drafts; Gmail changes require approval; Notion is one-way. User must review, submit and send.

## Claims vs implementation and limitations

1. **“Full-stack” means full workflow coverage through an agent harness, not a complete standalone product.** Core `/setup`, `/scrape` orchestration, `/rank`, `/apply`, `/interview`, `/outcome`, `/upskill`, `/notion-sync`, `/gmail-sync`, etc. are Markdown command/skill workflows; scripts/CLIs implement selected portions. The README's lifecycle diagram is therefore an operating recipe, not evidence every feature is a compiled program.
2. **Fit scores are rubric-driven LLM judgments.** Weighting, fit bands, and hard gates are specified; outputs depend on profile completeness, posting retrieval, model behavior and instructions. A score is not a calibrated probability of interview/hire. The rank spec explicitly calls scores triage and requires a later `/apply` evaluation.
3. **Search is constrained by available portals.** Four local boards are Denmark-specific. LinkedIn broadens geography but has its explicit ToS warning; freehire is tech-focused. Adding a new portal requires adapting/testing its skill. Coverage is not comprehensive job-market indexing.
4. **“Verified” has a narrow meaning.** PDF checking can test page count, text extraction, reading order by inspection, and specific date-range errors; it cannot validate all facts, guarantee ATS acceptance, or verify the external company is trustworthy. Factual grounding relies on profile comparisons and reviewer instructions.
5. **Research, salary, salary prediction and networking must not be conflated.** Research is web search by the LLM; salary numbers come only from the candidate's own dataset; LinkedIn outreach contacts are not found; no salary API or networking API is shipped.
6. **Automation does not mean autonomous applications.** It searches and drafts, tracks, proposes email-derived status changes and creates views, but does not fill/submit employer forms, send emails/messages, accept offers, or autonomously resolve stale cases.
7. **Success anecdotes are not efficacy evidence.** README reports the author's personal application funnel and outcome; this is a self-reported use case, not controlled evidence that the framework improves hiring outcomes ([README anecdote](https://github.com/ashishpatel26/ai-job-search/blob/30158c0493ae8ae1610769955ad04b189049afe8/README.md#L21-L39)).

## Reusable adoption patterns (observations, not recommendations)

- Keep LLM-authored career facts anchored to a canonical candidate profile and use the same record to gate fit, drafts and interview prep.
- Separate cheap bulk triage from expensive per-role research and drafting; persist short strengths/gaps with scores so decisions stay explainable.
- Use explicit `unreachable` versus `expired` states, retry windows, source provenance and reversible deadline sweeps rather than treating failed fetches as closed jobs.
- Make posting/email content untrusted input, bound web access, distinguish instruction-level defenses from sandboxing, and require user approval for persistent changes or external actions.
- Validate compiled artifacts, not only source: the repo checks actual PDF page counts/text extraction and flags layout defects.
- Preserve an append-only application archive and structured status history as inputs to future preparation and calibration.
- Treat optional integrations and BYO benchmark data as optional; represent unavailable data rather than inventing it.
