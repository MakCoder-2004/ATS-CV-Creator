# Plan the Pi SDK migration

**Status:** Historical pre-implementation plan, not current product guidance. See [implemented workflows](../workflows.md) and the [installed Pi validation](../validation/pi-sdk-installed-0.4.0.md). The status and proposed steps below describe the time this plan was written, not today's shipped app.

**Original status:** Plan for review. No application code or stored credentials changed.

## Goal and acceptance

CV Tailor uses a selected Pi `provider/model` and thinking level for every model request. Existing Pi authentication supplies credentials. Settings no longer accepts an OpenRouter key or local analysis-usage budgets. Old CV Tailor OpenRouter credentials are erased on an approved upgrade. The app retains explicit run-scoped consent, minimized outgoing data, evidence and citation checks, cancellation, safe file and storage limits, and draft approval.

Implementation is done only when an installed Windows app can, with a configured Pi account, analyze a posting, generate and review a cited CV, regenerate a section, run an optional faithfulness check, and structure an old PDF or DOCX CV into reviewable proposals. All model traffic must use Pi's model runtime. A locally missing credential, unavailable model, or incompatible thinking level must fail before a model request. A provider may reject a configured but expired credential only after dispatch; that failure must remain visible and must not silently retry. New runs must require fresh outgoing-data consent, including on an analysis cache hit. Closing and reopening the installed app must preserve the model settings and local records. Unit, public API, Electron, installer, and installed-app checks must pass. No app code has met this predicate yet.

## Scope and rigor

The current request paths are posting analysis, scoring and wording, factual and keyword repair, optional faithfulness comparison, regeneration, and profile-import AI. They are routed through `src/main/posting-analysis.ts`, `src/main/workbench.ts`, `src/main/source-linked-generation.ts`, and `src/main/profile-pdf-import-ipc.ts`. PDF and DOCX upload share the profile AI consent and generation path. The existing OpenRouter transport is `src/main/openrouter-analysis-transport.ts`. Settings, preload, IPC, consent, recovery, cache, backup, copy, and tests also reference it.

A repository search found 16 source files and 14 test files with OpenRouter terms. A separate search found 17 test files referring to budgets or capacity; these groups overlap. This is a rough impact count, not a promised edit count. Plan for eight implementation units and roughly three to six engineering days, plus access to an installed Windows app and a deliberately configured Pi account for a real provider check. The estimate is a guess. The largest unknowns are SDK bundling inside Electron, Pi credential availability outside the terminal session, model-specific effort support, and the representation of interrupted old runs.

Rigor is high because the migration changes a network and credential boundary, deletes a stored secret, and can change the claims in an exportable CV. Each unit requires a pre-change baseline, an independently observable result, and a stop condition. Pause before the multi-day implementation and again before any real credential deletion. An offline test must never be reported as proof that the installed app can authenticate or reach a provider.

## Design decision to settle first

The installed Pi SDK exposes `ModelRuntime.getModel()`, `getAvailable()`, and `completeSimple()`. The Pi model package exposes `getSupportedThinkingLevels()`. `completeSimple()` accepts a per-request reasoning level, abort signal, and maximum output tokens. A separate SDK option is `createAgentSession()` with an in-memory session, no tools, and a custom resource loader. That option requires explicit isolation from user and project extensions, skills, context files, and persisted transcripts. The current app needs one structured response per request, not a coding agent with tools.

**Provisional choice:** Use a pinned `@earendil-works/pi-coding-agent` dependency and its `ModelRuntime.completeSimple()` in the Electron main process. Reuse Pi's credential and model files through the SDK's supported agent directory, not a global executable or imported private installation path. Do not launch the Pi CLI, load its tools, or allow an LLM to edit files. Compare this choice with an isolated `createAgentSession()` using the architect and arena design review before locking the interface. Prove the chosen path in a throwaway, tool-free integration test before changing production request handling. If the SDK cannot authenticate or bundle safely in the installed app, stop and revise the design.

Replace the misleading `freeTierTermsAcknowledged` consent name and error with a provider-neutral privacy acknowledgement, without weakening the required acknowledgement. Store a single model reference as a provider and an exact model ID, plus one thinking level. Parse the Settings string against Pi's registered provider IDs, using an exact provider prefix and leaving the remaining string as the model ID. For example, `openrouter/author/model` has an OpenRouter provider and an `author/model` ID. Reject an ambiguous or unknown prefix rather than assuming that every provider ID lacks a slash. Resolve the exact chat model from Pi's registry and check for locally configured or discoverable authentication before dispatch. A configured but expired token can still fail at the provider. Reject unavailable models and thinking levels outside `getSupportedThinkingLevels(model)` before saving or dispatching. Do not silently clamp effort. A fresh installation with no selection offers an empty model field rather than assuming that an old OpenRouter ID names a Pi provider. Retain the selected model and effort in consent scope, analysis cache keys, generation recovery, and profile-import previews. The user enters a model reference and chooses a thinking level in the existing Settings layout. If Pi has no usable login, Settings tells the user to sign in with Pi outside CV Tailor and sends nothing.

Ask for schema-conforming JSON in each task prompt, then inspect the final response and parse it against the existing Zod schemas. Reject an empty response, tool call, provider error, cancellation, or output truncated at its ceiling. Keep bounded, task-specific maximum output sizes and raise them where the existing 2,048-token ceiling is too low. This is a response-shape and resource bound, not a daily usage quota. Define the per-task ceilings after representative saved postings and imports are measured. Pi and providers still enforce their own quotas and context limits. Remove app-specific daily and per-run attempt quotas, request pacing, and model-capacity metadata preflight. Do not remove upload or posting storage limits, JSON parsing limits, file/network security, or page-fit limits. Avoid unbounded automatic retries and uncertain duplicate charges. Keep explicit retry and cancellation behavior.

When an old SQLite workspace opens, migrate the model setting without silently treating `author/model` as Pi's `provider/model`. Keep previously saved drafts, source revisions, and attempt history readable. Treat old consents as invalid for Pi requests. Mark each pre-migration interrupted or uncertain generation as legacy and non-resumable. Keep the last saved draft, posting and profile history, and attempt history readable. Show a plain-language message that continuing needs a new outgoing-data preview, consent, analysis, and generation; never replay a prior uncertain attempt under Pi. A versioned recovery snapshot must not accept a missing effort level as authorization. The encrypted OpenRouter key is a ciphertext row in CV Tailor's `encrypted_credentials` SQLite table; Electron `safeStorage` encrypts and decrypts the bytes but does not own this row. Delete that row in a database transaction during the user-approved upgrade, without touching Pi's own credentials. Because the user chose deletion on upgrade, an approved release deletes the app-owned key automatically when the upgrade opens the workspace. The current planning approval does not authorize the release or delete a key. Test the migration with synthetic secrets; do not inspect, log, copy, or reveal a real key. Keep accepting structurally valid legacy backup settings, then drop `openrouter-model` and `analysis-budgets` on restore and require a new Pi model selection. The existing backup excludes `encrypted_credentials`, but a restore currently revokes old consents and removes locally stored credentials; preserve that behavior. Do not restore old authorization or resume legacy paused runs. Test an old backup with settings and consent rows, a synthetic encrypted-key row in the current workspace, a new-format backup, and interrupted migration.

## Sequence for the implementation run

1. **Capture the baseline and install gate.** Preserve pre-change outputs for focused unit tests, Electron Settings and consent flows, and a known installed build. Add offline fixtures for Pi model discovery, incompatible effort, cancellation, response shape, and absent auth before migrating behavior. Red tests must fail for the right observable reason. Confirm the pinned SDK builds and packages under Electron 39 on Windows. Stop if it cannot load in the installed main process.
2. **Prove a tool-free Pi request.** Compare the two SDK shapes with architect and arena. Send a harmless request with explicit model and effort through the selected SDK path in a bounded test environment. Inspect the returned provider, model, stop reason, and response, not only a successful promise. Demonstrate that project instructions and extensions are not loaded. Keep the runner out of production until this passes.
3. **Migrate settings and the stored secret.** Replace OpenRouter model and key controls with the Pi model and effort controls in the existing Settings structure. Check registry availability and effort before persistence. Preserve appearance and faithfulness preference. Test the upgrade and legacy-backup restore with synthetic keys. Erase the old encrypted key only after the user approves the implementation and destructive upgrade. Compare Settings screenshots in both themes and at desktop and narrow widths against its current baseline.
4. **Replace the shared model dispatch.** Remove OpenRouter HTTP transport, model-capacity preflight, daily and per-run attempt limits, and their Settings fields. Route requests through the chosen Pi runtime. Preserve run-bound authorization, abort, request accounting for recovery, bounded response sizes, finite retry policy, and failure reporting. Compare the old and new public API behavior with scripted provider results and no credentials.
5. **Move posting analysis and cache.** Bind cache entries to model and effort and retain fresh-run consent even on cache hits. Check new analysis, prior-analysis reuse, stale consent, malformed results, no-login failure, cancellation, and unchanged posting source. A cached analysis must not authorize generation under a new run.
6. **Move CV wording and recovery.** Send scoring, tailoring, repairs, optional faithfulness checks, and regeneration through the same model path. Check source IDs, parent citations, original profile facts, page targets, interrupted runs, and mismatched old snapshots. Verify the canonical document, actual PDF page measurement, approval, and export after a real run.
7. **Move old-CV structuring.** Use the selected Pi model and effort for both PDF and DOCX optional AI structuring. Keep local extraction usable without Pi login. Recheck the exact outgoing-text preview, run-specific consent, proposal provenance, late response discard, and explicit apply step. No AI proposal becomes a profile fact on receipt.
8. **Remove legacy code and validate the installed product.** Delete OpenRouter-only settings, transport, credentials UI, quota code, schemas, and obsolete tests after all callers migrate. Update `docs/architecture.md`, `docs/workflows.md`, and relevant Settings design disclosures; leave dated validation reports historical. Run focused checks per unit and the broad suite at integration. Package with physical dependencies, install the real NSIS build, sign in to Pi on that machine, exercise the three model workflows, export, close, and reopen. Verify the installed app reads Pi auth and native SQLite. Record cost-sensitive provider checks without disclosing credentials or private CV content.

Each unit starts with a hypothesis, changes one seam, and measures the visible result against its pre-change value. A unit is VERIFIED, NOT VERIFIED, or INCONCLUSIVE. Do not build the next dependent unit on an inconclusive one. Independent Settings UI and profile-import work may use separate worktrees after the shared contract is fixed; the dispatcher, schemas, database migration, and integration checks need one owner or serial integration. A delegated implementation gets an independent check of its diff and product behavior.

## Gates and open risks

- The pre-change baseline passed `npm run typecheck` and five focused Vitest files with 38 passing tests. Outputs are in `.audit/pi-sdk-typecheck.log` and `.audit/pi-sdk-baseline.log`. The first Vitest run failed 29 tests because the existing SQLite binding targeted Electron ABI 140 rather than Node ABI 137. After `npm rebuild better-sqlite3 --no-audit --no-fund`, all 38 passed. This is a corrected test-environment failure, not a behavioral regression. The Electron Settings and consent baselines and the installed-app baseline remain INCONCLUSIVE; record them before changing app code. Use `npm run typecheck`, `npm test`, `npm run build`, and focused Playwright in the repository's Node-then-Electron SQLite ABI order. For release, use `npm run dist:win`, an actual installation, and the installed-app checks in `docs/development.md`.
- Negative gates check that an absent Pi login, unavailable model, unsupported effort, changed model or effort after consent, stale cache run, oversized provider response, truncated JSON, late cancellation, bad evidence citation, and old recovery snapshot cannot trigger an unauthorized dispatch or export.
- Do not confuse removal of model-context preflight with support for an arbitrarily large posting. A provider may reject a request after consent; the app must keep the saved posting intact and report the failure plainly. Provider-side charges and quotas still apply.
- Pi login may use OAuth or environment credentials that are present in a terminal but absent in a GUI process. Installed Windows authentication and packaging remain INCONCLUSIVE until tested with a real provider. The chosen SDK version and license inventory need a release check.
- The plan is not a provider request or permission to delete an existing stored key. Those actions belong to the approved implementation run.

The decision trail for this planning run is `.audit/pi-sdk-migration.tsv`. It is local and ignored. If implementation starts, continue an auditable trail in a tracked artifact and link the verified results from the implementation PR.
