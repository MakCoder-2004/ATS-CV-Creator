# Plan Pi Web Access job intake and simpler model consent

**Status:** Historical, superseded proposal. The product now uses manual-only job intake under issue #116; this plan does not authorize URL fetching, search, Pi Web Access or altered consent. See [implemented workflows](../workflows.md).

**Original status:** Proposed plan for review. No application code, credentials, settings, or installed app changed.

## Goal and acceptance

A person can paste a job-posting URL and get the best effort read available through Pi Web Access on supported sources. After reviewing exact role identity, content, and source details, they can explicitly save an accepted posting and use the existing CV-tailoring workflow. The app falls back to manual paste when retrieval is unavailable or incomplete. It must not promise access to every posting or bypass login, CAPTCHA, paywall, or other access controls. LinkedIn remains blocked unless a suitable approved or licensed retrieval and retention route is established; the existing feasibility report does not establish one.

A person should authorize one model run once, not confirm each physical model request. The concise consent covers the bounded analysis and generation work for that run. Material changes to the posting, profile data, selected model, or operation require a fresh review and authorization. The current citation, evidence, authorization, recovery, and approval safeguards remain intact.

Acceptance requires observable behavior in the real Electron app:

- With deterministic source fixtures, direct fetch and search results either resolve to the exact requested role or are rejected; mismatched, incomplete, blocked, expired, unsafe, and unavailable results never become role evidence without clearly scoped user review.
- A supported web-access result can supply role text without Tavily-specific key setup. Only an explicit, reviewed save action may create a saved job; raw search results, cache files, unaccepted page text, and authorizations must not silently persist in jobs, profile facts, reusable consent, or backups.
- LinkedIn retrieval and saving remain disabled unless the review verifies an approved or licensed access route and downstream display, use, and retention rights. Public reachability or Pi Web Access success alone cannot pass this gate.
- In an installed Windows build, a representative set of public posting URLs can be fetched or searched through configured Pi Web Access. Access failures are surfaced honestly and offer manual paste. Login-gated, access-controlled, or uncertain pages remain unsupported rather than being bypassed.
- One explicit, concise consent authorizes the current operation and all its bounded internal model calls. A changed consent scope, declined consent, cancellation, or stale run causes no unauthorized provider dispatch. A cache hit does not authorize a different operation.
- A visible Electron test demonstrates one consent interaction for the run, then analysis and draft generation, including any bounded repair calls, without repeated confirmation screens. The user can inspect the exact outgoing-data details before authorizing; changes invalidate the prior authorization.
- Existing saved-job, manual-text, citation, CV review, export, backup, and recovery behavior remains compatible.

## Grounding and scope

Current code uses `fetchDirectJobResearch()` for a bounded direct HTTP read, and a separate Tavily adapter for limited indexed fallback on incomplete reads. Job research is volatile and distinct from saved jobs. `startAnalysis()` and draft generation use run-scoped authorization. The model dispatcher calls Pi's `ModelRuntime.completeSimple()` with `tools: []`; the installed app does not currently load Pi extensions or Pi Web Access. `pi-web-access` is not a project dependency. Its README describes a separate web-access package with provider configuration and MCP use, not a guarantee that every site's posting is public or available.

The current request has two workstreams and roughly 12 to 16 independently checked implementation units. Estimate eight to twelve engineering days plus Windows packaging and real-source verification. This is a planning estimate, not measured effort. Rigor is high because the changes add network/provider behavior, can transmit a public query or fetched page to third parties, add retained posting content, and reduce a user-facing model-authorization interaction. The consequential unknowns are which web-access integration can be safely packaged with this SDK version, which non-Tavily search/fetch providers and credentials are actually available in the installed app, what pages are accessible and permitted, whether the web-access cache can be disabled or reliably isolated and erased, and what the current confirmation burden is across operations.

### Blocking product decisions already answered

- When a page cannot be read, use best effort and fall back to manual paste. Search can be considered as an explicit fallback only when it can identify the exact role and disclose source/completeness; it must not guess a similar role.
- Keep explicit one-per-run consent. Do not introduce a remembered, standing permission.

### Constraints and open risks

Pi Web Access is an agent extension/MCP capability, while this app currently uses a tool-free completion API. Integrating it is not a one-line provider swap. An SDK agent session or MCP child process adds lifecycle, packaging, configuration, and trust boundaries; a project-owned web adapter that implements the same provider behavior may not satisfy the user's request to use Pi Web Access. Decide this through a focused prototype and architecture comparison before implementation.

Pi Web Access has a `fetch_content` capability for submitted URLs as well as search, but the integration prototype must prove both are available through the chosen SDK/MCP path. Its current package stores fetched content in a shared disk cache with a one-hour TTL, and its automatic search routing can select Tavily; neither default is acceptable without isolation and explicit configuration. Pin an allowlist of non-Tavily providers, disable automatic/paid fan-out, and disclose query destinations, credential requirements, and possible charges before enabling each provider. Do not assume the selected Pi model's sign-in authenticates web search over MCP. Search results and web access do not establish access rights, completeness, freshness, or exact identity. The existing LinkedIn feasibility report found no suitable approved direct LinkedIn route. Reassess LinkedIn access and downstream save/display/use/retention rights before enabling it. Never use account cookies, credentials, proxies, or provider functionality to evade a site's controls. Keep queries minimal and never include profile or CV data in job search.

The current Tailor CV run already accepts one run-scoped authorization that covers posting analysis, generation, and bounded repairs; it does not ask for each physical LLM call. Separate confirmation surfaces remain for regeneration and PDF/DOCX profile structuring, and the new saved-job import adds a source-review/save decision. The UX audit must count and judge each operation separately, including temporary research, generation, regeneration, and profile import. Do not claim that physical-call confirmations exist unless the visible baseline demonstrates them. Simplify repeated copy and avoid a second consent within one operation; keep one explicit scope-appropriate authorization for each genuinely distinct operation. Keep model disclosure distinct from search-provider disclosure; saving a posting does not authorize a model request.

## Proposed sequence and gates

1. **Capture pre-change evidence.** Record current job-link direct-read outcomes, incomplete-read/Tavily flows, consent interaction count, and public API and Electron behavior. Add a small fixture set covering public direct pages, search results, exact/mismatched role identity, login walls, incomplete text, unavailable links, redirects, and cancellation. Baseline must be captured before behavior changes.
2. **Prototype the Pi Web Access boundary.** In a disposable harness, prove both `fetch_content` on a user-submitted URL and `web_search` fallback through the candidate SDK/MCP path. Determine whether the installed SDK can load a pinned Pi Web Access extension or MCP server with isolated config, an explicit non-Tavily provider allowlist, no paid/default fan-out, bounded inputs/results, cancellation, no persisted sessions, and no unrelated project resources. Test its fetched-content disk cache: disable it if supported; otherwise isolate it in a per-run directory and prove cleanup on success, failure, cancellation, app close, and restart. If fetched pages cannot be prevented from persisting or reliably deleted, reject that integration path. Compare with an app-owned MCP child process, inspect package/runtime dependencies and license, and prove whether Pi model auth is available over MCP. Do not add credentials or launch the production app with the prototype. If neither route has a safe, supportable configuration, stop and revise the goal rather than pretending ordinary Pi tools are available to `completeSimple()`.
3. **Decide and document the source data shape.** Define an app-owned web retrieval attempt with submitted URL, selected role identity, provider/method, source URL, capture time, completeness, bounded text, uncertainty, and failure reason. Model search candidates separately from page text. Require exact role identity before promotion; prevent snippets, employer background, or similar-title results from becoming role evidence. Keep raw search results and unaccepted page text temporary and bounded. After clear review, an explicit save can create a saved job with source attribution and only the accepted posting fields. Define rights, freshness, correction, deletion, and retention requirements before saving fetched content. Keep any transient package cache out of shared Pi config, app backups, and durable caches; prove its deletion.
4. **Build the source verification harness.** Implement deterministic provider fakes and public-API tests before changing production retrieval. Check exact identity, mixed-source rejection, user acceptance, stale/cancel/expiry behavior, network limits, and no outbound profile data. Capture which source fields are shown to the user and how uncertainty is represented.
5. **Gate supported sources and persistence.** Review site terms and source rights for each enabled source. LinkedIn stays unsupported unless an approved or licensed route expressly supports the requested selected-job retrieval and downstream saving/display/use/retention. Do not use scraping or authenticated browser access as a workaround. For supported sources, define minimum completeness, attribution, freshness, correction, and deletion behavior before any job record migration.
6. **Integrate direct fetch and search separately.** Use Pi Web Access `fetch_content` on the submitted URL first where it can access the page safely. Use a pinned, non-Tavily `web_search` provider only as explicit best-effort fallback; no `auto` routing, paid provider, or surprise query fan-out. Require exact selected-role match and review before saving. Keep one user action bounded, cancellable, and limited in result size and provider attempts. Fail closed for login walls, access-control challenges, unsafe redirects, mismatch, or uncertain completeness. Remove Tavily-specific key UI and storage only after the replacement path is verified and all callers are migrated.
7. **Verify source behavior independently.** Run focused fixtures and public API tests per source unit. Then exercise visible intake in Electron using mocked public seams. Verify the actual source text, temporary-cache cleanup, and reviewed save into the ordinary saved-job-to-CV workflow rather than relying on a success status. Record actual installed behavior for each representative source, with unsupported cases listed plainly. Never claim universal site coverage from a fixture or search result.
8. **Map the current consent interaction.** Count visible decisions and LLM dispatches for Tailor CV analysis+generation, regeneration, PDF/DOCX profile structuring, and temporary research analysis. Inspect scope hash, run ID, model, profile/posting revisions, cache path, repairs, and cancellation behavior. The existing Tailor CV run already uses one authorization across analysis and generation. Record that baseline; don't invent extra confirmation screens. Set an explicit UX target for each operation and identify only redundant previews, repeated copy, or second consent prompts to remove.
9. **Design and test concise consent per operation.** Use one compact explicit authorization for each genuinely distinct operation with a short summary of data and destination, a clear start action, and optional expandable exact-data details. For the existing Tailor CV run, retain its one authorization across analysis, generation, and bounded repairs; remove redundant repeated copy or prompts only where the baseline shows they exist. Profile import, regeneration, and research each get one scope-appropriate authorization, not one per LLM call. Do not require repeated acknowledgements within the same unchanged bundle. Invalidate when scope changes. Keep web-search provider disclosure separate; user approval to send data to the model does not approve sending a query to a search provider.
10. **Validate the saved-job-to-CV workflow.** After source-specific rights and retention gates pass, test exact-role preview, corrections, explicit Save job, close/reopen, tailoring, citation review, and no leakage of unaccepted source text or temporary search cache. Check older manually saved jobs and manual paste stay unchanged.
11. **Integrate, document, and validate the real product.** Run focused tests after each unit, then the serial full test suite, typecheck, build, Electron tests, and an installed Windows check with the explicitly configured non-Tavily web-access provider. Verify network destinations and outgoing query content without logging secrets or private CV data. Verify temporary cache deletion on normal and interrupted paths, SQLite reopen for user-accepted job fields only, no Tavily or paid-provider dispatch, no unexpected model dispatch, and the stated per-operation consent interaction counts. Update current architecture/workflow and Settings/source disclosures; leave prior validation reports historical. Stop short of installer execution unless the user separately approves it.

## Verification verdicts and done condition

Each step is VERIFIED, NOT VERIFIED, or INCONCLUSIVE against its stated observable predicate. Inconclusive is not a pass. No implementation begins until the integration prototype demonstrates a real supported SDK/MCP seam and the user approves the plan. The whole change is done only when the source-access and one-consent predicates above pass in the real installed app; synthetic tests alone cannot establish site coverage or provider authentication.

## User impact and maintainer handoff

For the person preparing a CV, job-link intake becomes a best-effort convenience with honest manual fallback, and one concise authorization covers a complete model run instead of repeated confirmation screens. For the maintainer, the main new obligations are the external web-tool lifecycle/configuration boundary, exact-role evidence validation, deletion of obsolete Tavily configuration, and proof that authorization remains run-bound. No persistent authorization or source-content storage is proposed.
