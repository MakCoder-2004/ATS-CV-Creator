# Page composition contracts

## Shared shell

The production shell is the implemented four-page navigation: **Tailor CV**, **Saved jobs**, **My profile**, **Settings**. Desktop uses a 220px left rail with brand, vertical navigation, saved posting shortcuts and local-storage note; a 68px top header holds the Workspace / page breadcrumb and appearance control. A labeled control inside the rail may collapse it to a 64px icon rail, reclaiming document space while retaining the four page destinations. In the collapsed state, hide the saved posting shortcuts and storage note; expanding restores them. Remember this display preference on the device without changing job or page state. The page title and content begin on a shared 28px left edge. Current implementation hides the desktop header, job shortcuts and footer at 760px, moves appearance control into the compact top rail and displays navigation in a 4-column grid (2 columns below 520px). Preserve accessible page names and `aria-current` selected navigation. Keep both appearance controls if their duplicated responsive placement remains in implementation; expose one at a time visually.

## Tailor CV — prototype Variant A Workbench target

**Target reference:** `prototypes/cv-tailor-ui/src/App.tsx`, Workbench (Variant A), `src/index.css`, associated workflow/document/management components. Reproduce the approved composition, hierarchy, alignment and user-facing interaction patterns exactly. This page supersedes the current Tailor CV visual composition; actual production capabilities remain authoritative.

- Use the shared desktop rail and header. Rail contains brand/appearance, main navigation, saved jobs list with clear selected job state, a visible add-job affordance and a persistent local-only reassurance at its bottom.
- Main workspace starts with current-job context (company mark/name, role and posting identity) and workflow status. The five exact stage labels are **Job posting**, **Outgoing data**, **Generate**, **Review evidence**, **Export**. Use a horizontal, locally scrollable strip with inline numbered markers; identify the current stage with `aria-current="step"`, text and an underline. Reveal the current stage when narrow. Do not add extra top-level stages.
- Job posting shows the saved posting as the primary content and a secondary profile-source overview. Outgoing data shows the exact minimized posting and profile facts, selected Pi provider, model and thinking level, and privacy notice before one labeled authorization action. That action authorizes the run and starts posting analysis, including compatible cache reuse. Generate pauses to show required/preferred qualifications, tools/responsibilities and keywords before the separate **Generate tailored draft** action. Do not add another consent step for generation or repairs within the authorized run. Analysis is the main column with a secondary generation-action panel.
- During generation, replace the analysis workspace with an operation-driven progress checklist: Parse posting, Score evidence, Select content, Tailor paragraphs, Verify claims, Check document. Completion must follow actual operations, never timers. Cancellation, errors, interrupted-run recovery and real PDF page measurement remain available; do not show request counts or diagnostic state as primary user content.
- **User-approved review refinement:** Review evidence is document-first with a compact job/title band and a persistent review action bar above the document, not page-length/approval actions buried beneath a long CV or inspector. The bar names the next required action, shows real skill/check/page-fit state, exposes the wording acknowledgment, and keeps Check CV for issues, Check page length and Approve CV reachable while reading. It is sticky, not a fixed overlay; reserve focus scroll margins for its measured height. Keep Export as a separate phase. When the workspace can fit a 660px document track, a 20px gap and at least 400px of useful details width, contextual Review details may fill the remaining column; closing them leaves the document centered at its full readable size. Otherwise give the document the full workspace width and open details in an accessible dialog only when requested. Do not shrink the paper to preserve a side panel. Sources, New skills and Job match are the three named views, using controls at least 44px high. The Checks & options panel and its advanced AI-regeneration tools are removed by user decision; do not hide or recreate them elsewhere. Actual factual findings remain available from the existing review action bar, without an options panel. Selecting wording shows its linked source and why it appears immediately beneath the selected wording in the structured review document, with a dismiss action; the existing source inspector and its edit/record actions remain available. Inline context is review-only, never draft content, fit, approval, PDF or Word content. The document remains the visual anchor.
- Document workspace has a quiet toolbar above a white, Letter-proportioned review paper. Paper remains white in dark app mode and uses Lato, dark ink and restrained section dividers. The approved single-column artifact is identity/contact and an optional, concise CV professional title beneath the name, followed by populated Education, Experience, Projects and grouped Technical Skills sections. The title is a draft-local AI suggestion grounded in cited career facts and relevant to the posting, not a verbatim target posting title or a claim of unsupported seniority. If no safe title is supported, omit it. There is no narrative summary or Certificates. Generation and wording-only changes preserve original employment titles, employers, education institutions/degrees, project names and dates. The manual record editor may change those fields only as an explicit user-authored fact change with the chosen save scope. Education grades (GPA/CGPA) appear right-aligned beneath their dates, opposite the degree. Do not repeat the degree, institution, grade or matching dates as a description bullet; preserve distinct source-backed education details as bullets. Project technologies appear inline after the project name, with clickable project links right-aligned in the same heading row (never a separate link bullet). GitHub repository links display as `github/repository-name`, derived from the URL while preserving its original target; non-GitHub link labels stay unchanged. Long project names/tools may wrap without displacing the link from the top row. Skills are grouped as Languages, Technologies and Concepts. Render new and explicitly regenerated experience and project descriptions as one source-backed paragraph. Drafts without description-format metadata retain their released bullet rendering. Education descriptions and grouped skills keep their existing behavior. Render paragraph-format descriptions as paragraphs in review, PDF and Word exports. Review and generation stages show a selectable structured review layout that is explicitly not exact pagination; Export stage shows the actual compiled PDF preview. PDF is authoritative; the editable Word export may reflow.
- Paragraph and skill selection is visible but subtle; selected content reveals source/why-included context in the inspector. Editing and review controls remain attached to the relevant content and use plain verbs. The draft-local CV title can be edited or removed during Review without changing My profile or historical employment titles. An existing title remains locally editable/removable through the CV toolbar's small title editor. Review does not expose alternate-title or wording-regeneration options. Changes to this title create a new draft revision and invalidate checks, page fit and approval. Never resurrect legacy headline/summary fields or silently fill old drafts. Saved profile facts remain intact by default. Each manual add/edit/remove offers **This CV only** (default) or **This CV and my profile**, with explicit consequences and a fact declaration for additions/edits. Profile-scope changes update the current CV plus saved source history atomically; they do not silently rewrite other CVs. Draft-local facts are clearly identified as the user's additions, not AI-verified or saved-profile evidence.
- Posting-derived skills absent from the saved inventory appear as **Not in your profile** annotations in the review draft and in a secondary New skills to review panel. Each must be confirmed as a skill the person has or removed before approval/export. Confirmation is a draft-local user declaration, not profile evidence or permission to insert it into historical experience. Provide undo. Decisions and wording edits invalidate approval and page-fit/check state as appropriate. Never render pending/removed suggestions or review annotations into export files.
- Each Education, Experience, Projects and Technical Skills section exposes a visible Add action during review, including empty sections; select an existing entry to edit or remove its complete record. Forms use meaningful fields, never JSON or technical evidence selectors. Empty-section prompts and editing controls never appear in exports. Destructive profile removals state that they also remove the saved record and can affect other drafts.
- Qualification comparison consults the full profile and current draft-local facts, not just selected CV paragraphs or exact sentence matches. Show supporting source names and distinguish relevant evidence, partial evidence and requirements needing a closer look; distinguish related facts in the profile from sources actually linked in the CV. Never translate an uncertain local match into a categorical claim that the person lacks a qualification, infer tenure/production experience from a keyword, or present an ATS/hiring score.
- Review requires a fresh wording acknowledgment after draft or CV-title changes, passing factual checks and measured page fit. Export is a distinct clean-document stage with PDF/Word actions and a Back to review action. Returning to review may edit the approved document; any resulting revision requires renewed checks and approval.
- Inspector has a clear heading, selected paragraph context, evidence/source citation, associated keywords or gaps and explicit state. Source text is visually distinct with a slim interactive-colored rule; do not style evidence as a generic alert.
- Use prototype A typography refinement: Manrope UI, Sora headings; do not borrow B/C's IBM Plex-only or review-room alternative layouts. Light/dark themes are both supported.
- Preserve the prototype's information hierarchy and visible controls, but do not imply that fixture generation, coverage scores, simulated export, scenario toggles, fake state persistence or fixture-only content exist in production. If corresponding real behavior is unavailable, omit the unsupported action rather than shipping a simulation.
- Empty/blocked states explain the next available step without abandoning the document/workbench framing. Never indicate approval, evidence grounding, privacy filtering, export completion or generation completion until the real operation succeeds.
- Responsive: keep the document as the primary reading surface, preceded by its review action bar. Review details use the requested dialog when the workspace cannot fit the full document track and a readable details column; closing it restores focus to the opener or selected wording. Workflow stage navigation may scroll horizontally within its own region. No essential action relies on hover, page-bottom discovery, or a third narrow column.

### Optional cover-letter extension

The optional cover letter keeps the existing shell and five exact stages. Its implementation requirements are in `docs/plans/optional-cover-letter.md`; this contract does not establish that the feature ships.

- Put an unchecked **Include a cover letter** control in Outgoing data before authorization. Give it a persistent label and explain that enabling it adds model work for the same posting. The preview names the frozen purpose. A changed choice requires a refreshed preview and explicit authorization. Generate repeats that choice without silently extending consent, and preserves the posting-analysis pause.
- Within Review evidence and Export, use an accessible **CV / Cover letter** document selector inside the existing document workspace. Keep the document as the reading anchor and preserve separate status, acknowledgment, checks, measured fit, and approval for each document. Do not add another navigation destination or top-level stage. Do not imply that selecting a document approves it.
- The letter review paper is white, Letter-proportioned, and Lato in both app themes. Retain the approved template's contact header and letter structure, with a locally frozen date, subject, salutation, concise paragraph body, and local signature. The selectable review layout is not authoritative pagination. The actual compiled PDF in Export is authoritative. Do not show source annotations, edit controls, or acknowledgments in exported content.
- Show each letter paragraph with its actual linked source passages and parent labels available for review. Require a separate source acknowledgment for every current paragraph. Explain that automated checks do not prove semantic truth. Keep known unresolved findings visible and blocking. Edit wording locally without offering a profile-write scope.
- Provide a labeled optional recipient-name field in letter review. State that it stays on this device and is not sent to Pi. Use **Dear Hiring Manager,** when empty. Do not infer or automatically select saved job contacts. A recipient change invalidates letter review and fit just as a wording edit does.
- Keep the letter's review action bar, one-page check, and explicit approval reachable without navigating to the page bottom. Approved CV controls remain available when the letter is missing, failed, uncertain, stale, or unapproved. State those letter outcomes honestly rather than hiding the second document or moving the CV back to an incomplete state.
- A failed or uncertain letter offers an explicit, freshly authorized letter-only retry within the same five stages. Explain possible earlier provider charges for uncertain work. Do not retry automatically, regenerate the CV, or silently analyze again. If current source/model/posting bindings do not permit the bounded retry, explain the need for a fresh full flow.
- Export PDF and editable Word separately for the selected approved document, with document-specific labels. Show progress, cancellation, refusal, and success only for the operation that actually occurred. Word may reflow. Returning to review never silently changes approval until an edit occurs.

## Saved jobs — prototype page target

**Target reference:** the approved Workbench's Saved jobs management page in `prototypes/cv-tailor-ui/src/App.tsx` and related management component. Match its page-specific organization, not the production Saved jobs split editor/list redesign. Retain the production shared shell and real persistence, errors and validation.

- Page heading is left-aligned: context label “Your applications”, title “Give every CV a clear target.”, supporting sentence “Saved postings, drafts, and the evidence behind them.” and a right-aligned “New job” action.
- With saved jobs, show one bordered table with exactly three column roles: **Posting**, **Draft status**, **Next action**. Each full-width row presents title and company together on the first line where space permits, with the title primary and company secondary; long names wrap naturally. It also shows a truthful draft-state badge and the “Open posting” action. Selecting the row opens the posting in Tailor CV. Keep column alignments consistent between header and rows.
- With no saved jobs, show the prototype's one bordered/dashed empty-state surface: folder icon, “Your first job starts here” heading, explanatory paragraph and inline add-posting form. Keep the “New job” action available in the page heading too.
- Intake is manual-only: enter **Job title**, **Company**, and the complete posting text. Do not show a URL field, capture-mode selector, fetch/research action, refresh, or Open original action. Save is explicit and stores the job on this device.
- The inline form may repeat manually entered contact entries (name, role label, optional HTTPS profile URL), up to the domain limit. Contacts belong to the current saved-job record, are not posting revisions or CV/model input, and open externally only after an explicit **Open … profile** action. Reject localhost/private/intranet URL hosts; CV Tailor never fetches or inspects a profile or redirect.
- Preserve the prototype's closing history note beneath the list/state, but replace prototype-only copy with truthful production history/revision behavior. Do not claim history if none exists.
- Selected/hover/focus states are differentiated; selection is not conveyed by color alone. Long company/title/posting content wraps instead of widening the page.
- Keep the prototype's spatial organization and interaction sequence exactly; replace prototype fixtures and transient-only state with real application data. Do not retain the live app's split list/editor as the default Saved jobs page.
- Keep Draft status and Next action in stable, header-aligned columns regardless of posting length. On desktop, align the checkbox, first title line, company, Draft status and action controls on one clean shared row when the posting cell has room. Let long titles or companies wrap to another line within that cell instead of squeezing the status or actions. Use consistently aligned 44px row buttons: Open posting is primary, Edit is secondary, and Delete is separated and destructive. Keep desktop actions on one line and long posting text safely wrapped without widening the table. At narrow widths, stack row content and actions without horizontal scrolling.
- At narrow widths, preserve row information and reorder/stack actions without horizontal scrolling.
- Put selection controls inside Posting cells and the heading area without changing the three table columns. Place an accessible job checkbox beside each posting and a select-all control in a selection toolbar below the heading. Select all covers the jobs currently shown in the table. Keep an individual **Delete** action inside Next action beside Edit and Open posting; selecting or deleting a row never opens it.
- Keep the selected count visible and clear IDs that disappear after a refresh or deletion. A preview must succeed before the confirmation opens. The confirmation lists each actual title, company, and draft count, with the selected totals. Give **Cancel** initial focus. State that the selected postings, drafts, and local generation history are deleted, while profile facts and exported files remain. Say that this action cannot be undone from the workspace and that older backups may still contain the records.
- On cancel or refusal, keep the selection. For busy work, identify the affected posting and direct the person to stop the operation in Tailor CV. For stale previews, ask them to review the selection again. Disable repeated submit while deletion runs and show success only after storage commits.
- After success, refresh the table and sidebar shortcuts. If the active posting was deleted, clear its Tailor CV work and show the choose-a-posting state. Do not select another posting or start a model run automatically.
