# Page composition contracts

## Shared shell

The production shell is the implemented four-page navigation: **Tailor CV**, **Saved jobs**, **My profile**, **Settings**. Desktop uses a 220px left rail with brand, vertical navigation, saved posting shortcuts and local-storage note; a 68px top header holds the Workspace / page breadcrumb and appearance control. A labeled control inside the rail may collapse it to a 64px icon rail, reclaiming document space while retaining the four page destinations. In the collapsed state, hide the saved posting shortcuts and storage note; expanding restores them. Remember this display preference on the device without changing job or page state. The page title and content begin on a shared 28px left edge. Current implementation hides the desktop header, job shortcuts and footer at 760px, moves appearance control into the compact top rail and displays navigation in a 4-column grid (2 columns below 520px). Preserve accessible page names and `aria-current` selected navigation. Keep both appearance controls if their duplicated responsive placement remains in implementation; expose one at a time visually.

## Tailor CV — prototype Variant A Workbench target

**Target reference:** `prototypes/cv-tailor-ui/src/App.tsx`, Workbench (Variant A), `src/index.css`, associated workflow/document/management components. Reproduce the approved composition, hierarchy, alignment and user-facing interaction patterns exactly. This page supersedes the current Tailor CV visual composition; actual production capabilities remain authoritative.

- Use the shared desktop rail and header. Rail contains brand/appearance, main navigation, saved jobs list with clear selected job state, a visible add-job affordance and a persistent local-only reassurance at its bottom.
- Main workspace starts with current-job context (company mark/name, role and posting identity) and workflow status. The five exact stage labels are **Job posting**, **Outgoing data**, **Generate**, **Review evidence**, **Export**. Use a horizontal, locally scrollable strip with inline numbered markers; identify the current stage with `aria-current="step"`, text and an underline. Reveal the current stage when narrow. Do not add extra top-level stages.
- Job posting shows the saved posting as the primary content and a secondary profile-source overview. Outgoing data retains explicit sharing authorization. Authorization automatically starts posting analysis for that accepted run, including compatible cache reuse; Generate pauses to show required/preferred qualifications, tools/responsibilities and keywords before the explicit generation action. Analysis is the main column with a secondary generation-action panel.
- During generation, replace the analysis workspace with an operation-driven progress checklist: Parse posting, Score evidence, Select content, Tailor paragraphs, Verify claims, Check document. Completion must follow actual operations, never timers. Cancellation, errors, interrupted-run recovery and real PDF page measurement remain available; do not show request counts or diagnostic state as primary user content.
- **User-approved review refinement:** Review evidence is document-first with a compact job/title band and a persistent review action bar above the document, not page-length/approval actions buried beneath a long CV or inspector. The bar names the next required action, shows real skill/check/page-fit state, exposes the wording acknowledgment, and keeps Check CV for issues, Check page length and Approve CV reachable while reading. It is sticky, not a fixed overlay; reserve focus scroll margins for its measured height. Keep Export as a separate phase. At 1200px and above, contextual review details may occupy a 304px secondary column; closing them leaves the document centered at a readable size. Below 1200px, give the document the full workspace width and open details in an accessible dialog when requested. Do not shrink the paper to preserve a side panel. Sources, New skills, Job match and Checks & options are separately named views; selecting wording opens its source view. The document remains the visual anchor.
- Document workspace has a quiet toolbar above a white, Letter-proportioned review paper. Paper remains white in dark app mode and uses Lato, dark ink and restrained section dividers. The approved single-column artifact is identity/contact followed by populated Education, Experience, Projects and grouped Technical Skills sections; it contains no generated headline, narrative summary or Certificates. Generation and wording-only changes preserve original employment titles, employers, education institutions/degrees, project names and dates. The manual record editor may change those fields only as an explicit user-authored fact change with the chosen save scope. Education grades (GPA/CGPA) appear right-aligned beneath their dates, opposite the degree. Do not repeat the degree, institution, grade or matching dates as a description bullet; preserve distinct source-backed education details as bullets. Project technologies appear inline after the project name, with clickable project links right-aligned in the same heading row (never a separate link bullet). GitHub repository links display as `github/repository-name`, derived from the URL while preserving its original target; non-GitHub link labels stay unchanged. Long project names/tools may wrap without displacing the link from the top row. Skills are grouped as Languages, Technologies and Concepts. Render new and explicitly regenerated experience and project descriptions as one source-backed paragraph. Drafts without description-format metadata retain their released bullet rendering. Education descriptions and grouped skills keep their existing behavior. Render paragraph-format descriptions as paragraphs in review, PDF and Word exports. Review and generation stages show a selectable structured review layout that is explicitly not exact pagination; Export stage shows the actual compiled PDF preview. PDF is authoritative; the editable Word export may reflow.
- Paragraph and skill selection is visible but subtle; selected content reveals source/why-included context in the inspector. Editing and review controls remain attached to the relevant content and use plain verbs. Generated headline and professional-summary selection/editing are not part of the CV flow. Saved profile facts remain intact by default. Each manual add/edit/remove offers **This CV only** (default) or **This CV and my profile**, with explicit consequences and a fact declaration for additions/edits. Profile-scope changes update the current CV plus saved source history atomically; they do not silently rewrite other CVs. Draft-local facts are clearly identified as the user's additions, not AI-verified or saved-profile evidence.
- Posting-derived skills absent from the saved inventory appear as **Not in your profile** annotations in the review draft and in a secondary New skills to review panel. Each must be confirmed as a skill the person has or removed before approval/export. Confirmation is a draft-local user declaration, not profile evidence or permission to insert it into historical experience. Provide undo. Decisions and wording edits invalidate approval and page-fit/check state as appropriate. Never render pending/removed suggestions or review annotations into export files.
- Each Education, Experience, Projects and Technical Skills section exposes a visible Add action during review, including empty sections; select an existing entry to edit or remove its complete record. Forms use meaningful fields, never JSON or technical evidence selectors. Empty-section prompts and editing controls never appear in exports. Destructive profile removals state that they also remove the saved record and can affect other drafts.
- Qualification comparison consults the full profile and current draft-local facts, not just selected CV paragraphs or exact sentence matches. Show supporting source names and distinguish relevant evidence, partial evidence and requirements needing a closer look; distinguish related facts in the profile from sources actually linked in the CV. Never translate an uncertain local match into a categorical claim that the person lacks a qualification, infer tenure/production experience from a keyword, or present an ATS/hiring score.
- Review requires a fresh wording acknowledgment after draft changes, passing factual checks and measured page fit. Export is a distinct clean-document stage with PDF/Word actions and a Back to review action. Returning to review may edit the approved document; any resulting revision requires renewed checks and approval.
- Inspector has a clear heading, selected paragraph context, evidence/source citation, associated keywords or gaps and explicit state. Source text is visually distinct with a slim interactive-colored rule; do not style evidence as a generic alert.
- Use prototype A typography refinement: Manrope UI, Sora headings; do not borrow B/C's IBM Plex-only or review-room alternative layouts. Light/dark themes are both supported.
- Preserve the prototype's information hierarchy and visible controls, but do not imply that fixture generation, coverage scores, simulated export, scenario toggles, fake state persistence or fixture-only content exist in production. If corresponding real behavior is unavailable, omit the unsupported action rather than shipping a simulation.
- Empty/blocked states explain the next available step without abandoning the document/workbench framing. Never indicate approval, evidence grounding, privacy filtering, export completion or generation completion until the real operation succeeds.
- Responsive: keep the document as the primary reading surface, preceded by its review action bar. Review details use the requested dialog below 1200px; closing it restores focus to the selected wording. Workflow stage navigation may scroll horizontally within its own region. No essential action relies on hover, page-bottom discovery, or a third narrow column.

- Preserve the prototype's closing history note beneath the list/state, but replace prototype-only copy with truthful production history/revision behavior. Do not claim history if none exists.

### Approved link-intake and refresh extension (issue #28)

The user-approved intake extension adds a compact add-posting panel to this page; it does not replace the Saved jobs table, change its three column roles, add a workspace destination, or redesign the shared shell. Keep the existing page heading and **New job** action. The intake offers two explicit capture choices: **Import from link** and **Paste posting text instead**. Selecting a choice reveals its labeled form in the page; the manual text route remains a complete alternative.

- Link entry shows the parsed source hostname as the person types. Pasting, opening the intake and reopening a saved job make no request. Fetching starts only after **Fetch posting** (or the explicit **Refresh** action). Unknown or unsupported sources explain the limitation and offer **Open original posting** or **Paste posting text instead**; the prototype's synthetic responses are not source support evidence.
- Fetch and extraction lead to a temporary review preview, not a saved job. Show title, company, optional metadata as unknown when absent, and the complete readable posting. Keep the captured source snapshot distinguishable from the person's editable working values/text; label missing legacy/manual provenance as **Unknown** rather than inventing a source. Surface material field conflicts and incomplete essential content for resolution before save.
- **Save job** is a separate explicit action from fetch/review and from any model analysis. Unsaved preview data is temporary. Warn before discarding a preview with edits; make no promise of recovering it after exit. A successful saved job retains its source snapshot, accepted working posting and revisions as separate, readable versions.
- An unchanged exact duplicate offers **Open existing** without creating a job or revision. A changed source offers **Review changes**. Compare the previous source snapshot, current working posting and newly fetched source together; preserve the working version until the person explicitly accepts changes. Never auto-merge or overwrite on refresh.
- Preserve the existing table organization and provide truthful fetch, extraction, saving, cancellation and error feedback. A retry is always an explicit new attempt. A cancelled or superseded operation cannot replace the current preview or mutate a saved job after a late response.
- Keep complete long text inspectable. Never truncate it silently. If a posting exceeds a supported storage ceiling, explain refusal without saving a partial posting; if model input is too large, keep storage and analysis eligibility distinct and offer an appropriate explicit next step without silently shortening the source.
- Keep source links and text readable and inert; do not expose raw HTML, JSON, run IDs or technical extraction selectors. The prototype's fixture-only controls, sample outcomes and in-memory state are not production requirements.
- At supported narrow widths, stack intake fields and source/working/new-source comparisons in reading order, keep all actions reachable and prevent page-level horizontal scrolling. Preserve keyboard use, visible focus and announced operation status; do not add a third narrow column.
